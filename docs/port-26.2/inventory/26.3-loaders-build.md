# Capsule 26.2 -> 26.3: loader APIs and build tooling (and one toolchain for both)

Companion to `docs/port-26.2/inventory/loaders-build.md` (cited below as **LB §n**). Scope: the versions and tools of
the 26.3 step, the NeoForge and Fabric API changes 26.2 -> 26.3 in the loader glue that the 26.2 port produces
(LB §3, §4), and CI/scripts. Vanilla 26.3 changes are the other inventories' business
(primer: https://raw.githubusercontent.com/neoforged/.github/main/primers/26.3/index.md, 5844 lines). Where a vanilla
change sits inside loader glue (GameTest `TestData`, render stage choice) it is listed here.

How this was checked (2026-11-23): maven metadata of NeoForged, Fabric, Nucleoid, BlameJared, Shedaniel; Modrinth API;
piston-meta; **NeoForge 26.2.0.95 vs 26.3.0.115 sources** (file list diff + per-file diff of every class the glue uses);
**FancyModLoader 11.0.16 vs 12.0.16 sources**; NeoForge 26.3.0.115 moddev-config, changelog and installer
(`data/unix_args.txt`); **`javap -public` of every API class of all 45 Fabric API modules, 0.161.0+26.2 vs 0.167.0+26.3**,
plus `fabric-gametest-api-v1` 4.0.22 vs 4.0.37 and the `fabric-rendering-v1` 26.3 sources; FCAP 26.2.1 vs 26.3.1 jars;
`javap` on the vanilla 26.2 and 26.3 client jars; the Fabric 26.3 blog post, docs.fabricmc.net porting page, the
fabricmc.net/develop page script, fabric-example-mod `26.3`, NeoForge MDK-26.3-ModDevGradle, MultiLoader-Template
`26.3`; and **real builds** of a skeleton multiloader project (§2). Anything not checked that way is **UNVERIFIED**.

## 2. Toolchain trial

### 2.1 The skeleton
`docs/port-26.2/toolchain-trial/` mirrors Capsule's layout:
- `settings.gradle`: Capsule's `pluginManagement` (plugin portal, NeoForged maven, Fabric maven as `exclusiveContent`
  for `net.fabricmc`), foojay 1.0.0, `include common, neoforge, fabric`.
- root `build.gradle`: `net.neoforged.moddev` `${mdg_version}` and `net.fabricmc.fabric-loom` `${loom_version}`, both `apply false`.
- `buildSrc/` with `multiloader-common.gradle` (java-library, Java 25 toolchain, `mavenCentral` excluding `net.fabricmc*`,
  `gametest` source set) and `multiloader-loader.gradle` (Capsule's `commonJava`/`commonResources` consumable
  configurations; the loader's `compileJava` sources common's sources, `processResources` adds common's resources).
- `common`: MDG vanilla mode `neoFormVersion = neo_form_version`, `addModdingDependenciesTo(sourceSets.gametest)`,
  `artifacts { commonJava …; commonResources … }`; class `trial.common.TrialCommon` uses `net.minecraft.resources.Identifier`.
- `neoforge`: MDG `version = neo_version`, runs `client`/`server`/`gameTestServer`, `mods { trial }`; `@Mod` class using
  `Identifier`, `IEventBus`, `ModContainer`, `AddServerReloadListenersEvent`; `neoforge.mods.toml`.
- `fabric`: non-remapping `net.fabricmc.fabric-loom`, `minecraft`, `implementation` fabric-loader and fabric-api,
  `loom.mods { trial; 'trial-gametest' }`, a `gameTestServer` run with `-Dfabric-api.gametest`;
  `ModInitializer` using `Identifier`, `ServerTickEvents.END_LEVEL_TICK`, `ResourceLoader`.
- Java: the image has only JDK 21 (`/usr/lib/jvm`); the JDK 25 (Temurin 25.0.4.1) that foojay had provisioned in
  `~/.gradle/jdks` was used as `JAVA_HOME`, with Capsule's `gradle/gradle-daemon-jvm.properties` (toolchainVersion=25).
- Runner: `(trial run output, not kept) <name> <gradle> <loom> <mc> <neo> <neoform> <fapi>`
  rewrites `distributionUrl` and `gradle.properties`, then runs
  `./gradlew clean build --warning-mode all --max-workers=2 --init-script central-mirror.init.gradle`.
  Logs: `(trial run output, not kept)`.
  (The init script only swaps Maven Central for a mirror, see §5 item 8.)

## 3. NeoForge 26.2.0.95 -> 26.3.0.115: changes in Capsule's loader glue

Summary: the glue of LB §3 compiles unchanged on 26.3 **except** the config type rename (§3.1, required), the GameTest
`TestData` constructor (§3.4, required) and the render stage choice (§3.3, behavioural). `IItemHandler` and the whole
`net.neoforged.neoforge.items` package are gone, which LB §3.3/§3.9 already replace.

Per-file diff of the APIs LB §3 relies on, all **unchanged** 26.2.0.95 -> 26.3.0.115: `SortedReloadListenerEvent`,
`RecipesReceivedEvent`, `RegisterRangeSelectItemModelPropertyEvent`, `RegisterColorHandlersEvent` (`ItemTintSources`),
`EntityRenderersEvent`, `SubmitCustomGeometryEvent`, `ClientPacketDistributor`, `PacketDistributor`,
`RegisterPayloadHandlersEvent`, `PayloadRegistrar`, `Capabilities` (`Capabilities.Item.BLOCK` =
`BlockCapability<ResourceHandler<ItemResource>, @Nullable Direction>`), `ResourceHandler`, `ItemUtil`, `Transaction`,
`GameTestHooks`, `RegisterGameTestsEvent`, `FakePlayerFactory`, `EntityJoinLevelEvent`, `EntityLeaveLevelEvent`,
`LevelEvent`, `PlayerTickEvent`, `LevelTickEvent`, `PlayerInteractEvent`, `RegisterCommandsEvent`, `ServerStartingEvent`,
`ServerStoppedEvent`, `ClientChatReceivedEvent`, `ClientTickEvent`, `ItemInstanceExtension` (`getCraftingRemainder()`),
`IBlockEntityRendererExtension`. FML: `ModList`, `FMLPaths`, `FMLEnvironment`, `EventBusSubscriber`, `@Mod` unchanged.
Only cosmetic or additive changes: `AddServerReloadListenersEvent` (the deprecated `getRegistryAccess()` is removed;
`addListener(Identifier, PreparableReloadListener)` is unchanged), `OnDatapackSyncEvent` (`sendRecipes(RecipeType...)`
unchanged, javadoc only), `ExtractLevelRenderStateEvent` (adds `getOptionsRenderState()`), `ItemResource`/`BlockSnapshot`
(`equals(@Nullable Object)`), `BlockEvent` (javadoc), `DeferredRegister` (adds a `registerEntityType` overload),
`IItemExtension` (`onEntityItemUpdate`, `supportsEnchantment`, `isPrimaryItemFor` unchanged), `IBlockStateExtension`
(`rotate(LevelAccessor, BlockPos, Rotation)` unchanged), `IEntityExtension` (`getPersistentData()` unchanged).
The installer's server args still end with `net.neoforged.fml.startup.Server` and FML 12 still has
`net.neoforged.fml.startup.GameTestServer`, so LB §5.5's `prod-gametest.sh` entrypoint swap is unchanged.

### 3.1 Config types renamed (FML 12, NeoForge 26.3.0.37 "Rename COMMON and SERVER config types to LOCAL and SYNCED")
`net.neoforged.fml.config.ModConfig.Type` in FML 12.0.16 is `LOCAL, CLIENT, SYNCED, STARTUP`. `COMMON` and `SERVER`
**no longer exist**, so `CapsuleNeoForge.java` line 43 (`modContainer.registerConfig(ModConfig.Type.COMMON, config)`) does
not compile. The default file name is `<modid>-<type>.toml`, so the plain rename would silently move Capsule's config
from `config/capsule-common.toml` to `config/capsule-local.toml` (existing user settings ignored,
`scripts/prod-smoke.sh` line 79, `TEST.md`, `Config.java` javadoc line 39 and `CHANGELOG.md` all name
`capsule-common.toml`). Replacement (keeps the file):
```java
// LOCAL = the former COMMON (both sides, not synced); keep the pre-26.3 file name
modContainer.registerConfig(ModConfig.Type.LOCAL, config, "capsule-common.toml");
```
(`ModContainer#registerConfig(ModConfig.Type, IConfigSpec, String fileName)` exists in FML 12.0.16.)
`CapsuleNeoForgeClient` (LB §3.2, `ModConfig.Type.CLIENT`): unchanged.
**Fabric is different**: FCAP 26.3.1 still ships FML 11's `ModConfig$Type` with `COMMON, CLIENT, SERVER, STARTUP`
(javap of the 26.3.1 Fabric jar), and `fuzs.forgeconfigapiport.fabric.api.v5.ConfigRegistry` is byte-for-byte the same
API as 26.2.1. So LB §4.1's `ConfigRegistry.INSTANCE.register(CapsuleMod.MODID, ModConfig.Type.COMMON, config)` stays
`COMMON` on Fabric (file `capsule-common.toml`). The two loaders now name the type differently; that is fine because
the registration lines are in loader code. `ModConfigSpec` (NeoForge 26.3) only changed its `GAME` restart type to map to
`SYNCED`.

### 3.2 `IItemHandler` / `net.neoforged.neoforge.items.*` removed
The whole package is deleted in 26.3 (`IItemHandler`, `IItemHandlerModifiable`, `ItemStackHandler`, `ItemHandlerHelper`,
all `wrapper.*`), as are `IFluidHandler`, `FluidUtil`, `IEnergyStorage`. LB §3.3 (`NeoForgePlatform`, `ItemHandlerSource`
→ `ResourceHandler<ItemResource>`) and LB §3.9 (`NeoForgeTestUtils`, `SophisticatedStorageTests`) already move off them
in the 26.2 port. Action for 26.2: do those replacements **fully** (no `@SuppressWarnings("removal")` stop-gap on
`IItemHandler`), otherwise the 26.3 build breaks. `MekanismTests` (uses `ItemHandlerHelper`) is excluded by D5.

### 3.3 Render stages: Order Independent Transparency (26.3 "improved transparency")
NeoForge 26.3 `RenderLevelStageEvent` javadoc: with `GameRenderer#useImprovedTransparency()` the order is
`AfterSky, PrepareRenderBuffersEvent, AfterOpaqueBlocks, AfterOpaqueFeatures, OitTranslucent, AfterLevel`; **only
without it** do `AfterTranslucentFeatures, AfterTranslucentBlocks, AfterTranslucentParticles, AfterWeather` fire. Every
stage but `AfterSky`/`AfterLevel` now carries an active `RenderPass` (`getRenderPass()`, "must be used instead of
creating a custom one", buffer uploads must happen in the new `PrepareRenderBuffersEvent`).
Effect on LB §3.2 (`RenderLevelStageEvent.AfterTranslucentBlocks` for `CapsulePreviewHandler.onLevelRenderLast`): with
improved transparency on, **the capsule preview would not be drawn at all**. Replacement for the rendering agent, in
order of preference:
1. extraction + submit, which works with both transparency modes: `ExtractLevelRenderStateEvent` (store the preview data
   with `LevelRenderState#setRenderData`) + `SubmitCustomGeometryEvent#getSubmitNodeCollector()` (unchanged 26.2 ->
   26.3). This is also the Fabric-equivalent path (§4.2).
2. if it must draw immediately: listen to **both** `RenderLevelStageEvent.AfterTranslucentBlocks` and
   `RenderLevelStageEvent.OitTranslucent` (filter `getOitStage()` to one stage, **UNVERIFIED** which one suits a
   translucent overlay), and draw through `event.getRenderPass()`.
Decide this in the 26.2 port (option 1 needs no change at 26.3).

### 3.4 GameTest instances: `TestData` has a dimension (vanilla 26.3, inside LB §3.9)
Vanilla 26.3 `net.minecraft.gametest.framework.TestData` long constructor is now
`TestData(EnvironmentType, ResourceKey<Level> dimension, Identifier structure, int maxTicks, int setupTicks, boolean required, Rotation, boolean manualOnly, int maxAttempts, int requiredSuccesses, boolean skyAccess, int padding)`
(26.2: same without `dimension`; the 5- and 6-argument constructors are unchanged). LB §3.9 step 2 becomes:
```java
event.registerTest(t.id(), new FunctionGameTestInstance(ResourceKey.create(Registries.TEST_FUNCTION, t.id()),
        new TestData<>(env, Level.OVERWORLD, t.structure(), t.maxTicks(), t.setupTicks(), t.required(),
                Rotation.NONE, false, t.maxAttempts(), t.requiredSuccesses(), false, 1)));
```
Tip for the 26.2 port: build the `TestData` in one common helper (`CapsuleTest#testData(Holder env)`), so 26.3 changes one
line for both loaders (Fabric §4.4 uses the same constructor). `RegisterGameTestsEvent` (`registerEnvironment`,
`registerTest`) and `TestEnvironmentDefinition.AllOf(List)` are unchanged.

### 3.5 Other NeoForge 26.3 changes checked, no Capsule action
- `LootTableLoadEvent#getRegistries()` now returns `HolderGetter.Provider` (was `HolderLookup.Provider`); Capsule only
  calls `getName()`/`getTable()` (LB §3.1 line 64-67). Loot tables are a reloadable registry in 26.3 but the event still
  fires per table.
- `DeferredHolder` now `extends Holder.Reference<R>` (26.3.0.45); `HolderExtension#getKey` throws for non-reference
  holders, use `keyOrNull` (26.3.0.52). Capsule's glue only uses `DeferredRegister#register(...)` and `.get()`.
- `IItemExtension#damageItem(..., Consumer<ItemStack>)` (was `Consumer<Item>`), `getBurnTime` removed (fuel is a data
  component), `getEquipmentSlot` deprecated for removal: none of them is overridden or called anywhere in Capsule
  (grep over `common/`, `neoforge/`, `fabric/` sources).
