# Capsule port inventory: Minecraft 1.21.1 → 1.21.2/1.21.3 (NeoForged primer slice)

Source primer: `primers/1.21.2.md` (3199 lines, read in full). Repo: the repository root at `5cebb7c`.
All paths are relative to the repo root. Line numbers come from the current tree.

The port goes straight to 26.2, so each entry says whether the API changes again later. When it does, apply the
1.21.2 change only as an intermediate step and check the later inventories before writing final code.

Legend: **[COMPILE]** = compile error once the 1.21.2 jars are on the classpath. **[SILENT]** = still compiles but behaves
wrong or crashes at runtime. **[DATA]** = JSON/resources. **[TEST]** = only gametest/unit-test sources.

---

## 0. Highest-impact summary (read first)

1. **Recipes are no longer synced to the client** (section 6.1). The client has no `RecipeManager`, so the creative tab,
   JEI/REI/EMI lists and the Fabric `ClientPacketListenerMixin` all break. This needs a design change: either a Capsule S2C
   payload, or the loaders' recipe-sync APIs.
2. **The recipe API has been rewritten** (sections 6.2–6.6). Every one of the 8 recipe classes is affected:
   `getResultItem`, `getIngredients`, `canCraftInDimensions`, `Ingredient.EMPTY`, `CODEC_NONEMPTY`,
   `SimpleCraftingRecipeSerializer`, `RecipeHolder` ids, `NonNullList<Ingredient>` and `placementInfo`.
3. **Ingredient JSON is now a HolderSet string** (section 6.7). All 34 recipe JSON files with `{"item":…}`/`{"tag":…}` keys
   have to be rewritten, along with the prefab template JSON and the code that generates it.
4. **`Item.Properties#setId` and `BlockBehaviour.Properties#setId` are now mandatory.** Without them the game crashes at
   registration (section 2). `BlockEntityType.Builder` is also gone (section 3).
5. **`Item#use` now returns `InteractionResult`** (section 4), and **enchantability is now the `ENCHANTABLE` component**
   (section 5).
6. Smaller items: level heights (`getMinY`/`getMaxY`), `neighborChanged(Orientation)`, `MobSpawnType` → `EntitySpawnReason`,
   `GameRenderer::getPositionColorShader` → `CoreShaders`, `LevelRenderer.renderLineBox` → `ShapeRenderer`,
   `Registry#get`/`asLookup`/`getOrCreateTag`, `PreparableReloadListener#reload` without profilers, `FakeWorld#getMaxLightLevel`.

## 1. Interaction Results (primer "Interaction Results", l.1049)

**What changed:** `InteractionResultHolder<T>` and `ItemInteractionResult` were removed and merged into the sealed
interface `InteractionResult`. `Item#use(Level, Player, InteractionHand)` and `ItemStack#use` now **return
`InteractionResult`**. The constants are `SUCCESS` (swing on client), `SUCCESS_SERVER`, `CONSUME`, `FAIL`, `PASS` and
`TRY_WITH_EMPTY_HAND`. `sidedSuccess` no longer exists. To replace the held stack, use
`InteractionResult.SUCCESS.heldItemTransformedTo(stack)`. `BlockBehaviour#useItemOn` also returns `InteractionResult`.

**Affected locations**
- [COMPILE] `common/src/main/java/capsule/items/CapsuleItem.java:39`: `import net.minecraft.world.InteractionResultHolder;` (remove)

- [COMPILE] `common/src/main/java/capsule/items/CapsuleItem.java:606`: `return new InteractionResultHolder<>(InteractionResult.FAIL, capsule);`
- [COMPILE] `common/src/main/java/capsule/items/CapsuleItem.java:653`: `return new InteractionResultHolder<>(InteractionResult.SUCCESS, capsule);`

  `NeoForgeTestUtils.java:47`), so those stay as they are. `fabric/.../CapsuleFabric.java:76` (`AttackBlockCallback`) also stays.

**Instructions**

## 2. Registry Object Id in the Properties (primer l.1448) + Item Names and Models (l.703)

**What changed:** `Item.Properties#setId(ResourceKey<Item>)` and `BlockBehaviour.Properties#setId(ResourceKey<Block>)`
**must** be called before the properties are passed to the `Item`/`Block` constructor. Otherwise the constructor throws.
The id sets the default `ITEM_NAME`/description id, the `ITEM_MODEL` (`<ns>:<path>` → `models/item/<path>.json`) and the
block's default loot table. A `BlockItem` must also call `useBlockDescriptionPrefix()` to keep the `block.<ns>.<path>`
translation key. Without it the key becomes `item.<ns>.<path>`.

**Affected locations**
- [SILENT→crash] `common/src/main/java/capsule/items/CapsuleItem.java:146-152`: constructor `super((new Item.Properties()).stacksTo(1).durability(0).fireResistant());` has no id.
- [SILENT→crash] `common/src/main/java/capsule/items/CapsuleItems.java:36`: `Services.PLATFORM.register(BuiltInRegistries.ITEM, "capsule", CapsuleItem::new)`
- [SILENT→crash] `common/src/main/java/capsule/blocks/BlockCapsuleMarker.java:27-31`: `super(BlockCapsuleMarker.Properties.of().mapColor(MapColor.STONE).strength(2.5F).sound(SoundType.STONE));`
- [SILENT→crash] `common/src/main/java/capsule/blocks/CapsuleBlocks.java:13`: `register(BuiltInRegistries.BLOCK, "capsulemarker", BlockCapsuleMarker::new)`
- [SILENT→crash + wrong name] `common/src/main/java/capsule/blocks/CapsuleBlocks.java:14`: `new BlockItem(CAPSULE_MARKER.get(), new Item.Properties())`.
  The lang file only has `block.capsule.capsulemarker` (`assets/capsule/lang/en_us.json:12`), so `useBlockDescriptionPrefix()` is required.
- Loader registration is generic (`neoforge/.../NeoForgePlatform.java:68-73` uses a plain `DeferredRegister`, `fabric/.../FabricPlatform.java:122-125`
  uses `Registry.register`), so neither loader sets the id automatically. It must be passed in from common code.

**Instructions**
```java

public static ResourceKey<Block> blockKey(String name) { return ResourceKey.create(Registries.BLOCK, ResourceLocation.fromNamespaceAndPath(MODID, name)); }

// CapsuleItem

    super(properties.stacksTo(1).durability(0).fireResistant().enchantable(5)); // enchantable: see section 5
    DispenserBlock.registerBehavior(this, new DispenseCapsuleBehavior());
}
// CapsuleItems:36
Services.PLATFORM.register(BuiltInRegistries.ITEM, "capsule", () -> new CapsuleItem(new Item.Properties().setId(CapsuleMod.itemKey("capsule"))));

// BlockCapsuleMarker
public BlockCapsuleMarker(BlockBehaviour.Properties properties) {
    super(properties.mapColor(MapColor.STONE).strength(2.5F).sound(SoundType.STONE));
}
// CapsuleBlocks:13
register(BuiltInRegistries.BLOCK, "capsulemarker", () -> new BlockCapsuleMarker(BlockBehaviour.Properties.of().setId(CapsuleMod.blockKey("capsulemarker"))));
// CapsuleBlocks:14

```
`fireResistant()` still exists in 1.21.2 and now sets the `DAMAGE_RESISTANT` component, so it needs no change.
`CapsuleItem#getName(ItemStack)` (l.373-420) still overrides `Item#getName(ItemStack)` and stays as it is.

Item models need no edit: `models/item/capsule.json` and `models/item/capsulemarker.json` match the default `ITEM_MODEL`,
and there are no clashing root `models/<name>.json` files.

**Later versions:** `setId` is stable. Item models change in **1.21.4** (`assets/<ns>/items/*.json` definitions, and
`ItemProperties`/predicate overrides are removed). The models are therefore only valid until 1.21.4.

## 4. Orientations: `neighborChanged` (primer "Orientations", l.1991)

**What changed:** `BlockBehaviour#neighborChanged(BlockState, Level, BlockPos, Block, BlockPos fromPos, boolean)` is now
`neighborChanged(BlockState, Level, BlockPos, Block, @Nullable Orientation, boolean)` (`net.minecraft.world.level.redstone.Orientation`).
`updateShape` was also reordered, but Capsule does not override it.

**Affected locations**

**Instructions**
```java

    ... // body unchanged (does not use pFromPos)
}
```

## 5. Enchantable, Repairable Items (primer l.709) + Technical Changes to Items (l.919)

**What changed:** `Item#getEnchantmentValue()`, `Item#isEnchantable(ItemStack)` and `Item#isValidRepairItem` were removed.
Enchantability is now the `DataComponents.ENCHANTABLE` component (`Enchantable(int value)`), set with
`Item.Properties#enchantable(int)`. Without it, `ItemStack#isEnchantable()` is false and
`EnchantmentHelper.selectEnchantment` returns nothing, so the enchanting table offers nothing.

**Affected locations**
- [COMPILE] `common/src/main/java/capsule/items/CapsuleItem.java:422-425`: `@Override public int getEnchantmentValue() { return 5; }`
- [COMPILE] `common/src/main/java/capsule/items/CapsuleItem.java:427-430`: `@Override public boolean isEnchantable(ItemStack stack) { return !CapsuleItem.hasState(stack, CapsuleState.ONE_USE); }`
- Related: `CapsuleItem.java:443-445` (`isPrimaryItemFor`, NeoForge `IItemExtension`), `fabric/.../CapsuleFabric.java:80-81` (`EnchantmentEvents.ALLOW_ENCHANTING`).
- [TEST] `common/src/gametest/java/capsule/gametest/RecallTests.java:45-58` (the enchanting-table test) only passes once the component is set.

**Instructions**
- Delete both overrides. Add `.enchantable(5)` to the properties (see the section 2 snippet).
- To keep "one-use capsules cannot be enchanted at a table", move the check into the per-stack hook that already exists
  (common code, used by NeoForge as `IItemExtension#isPrimaryItemFor`):
```java
public boolean isPrimaryItemFor(ItemStack stack, Holder<Enchantment> enchantment) {
    if (CapsuleItem.hasState(stack, CapsuleState.ONE_USE)) return false;
    return CapsuleEnchantments.acceptsLoyalty(stack, enchantment) || enchantment.value().isPrimaryItem(stack);
}
```
  On Fabric, `ALLOW_ENCHANTING` (`CapsuleFabric.java:80`) receives an `EnchantingContext`. Return `TriState.FALSE` for
  `ONE_USE` stacks in the `PRIMARY` context if that behaviour must be kept. This is loader API, so check the Fabric API version.
- `durability(0)`/`stacksTo(1)` are unchanged. **Later versions:** the ENCHANTABLE component is stable.

## 6. Recipes, now in Registry format (primer l.1482–1860) + The Ingredient Shift (l.1262) + Holder Set Transition (l.13)

### 6.1 Recipes are no longer sent to the client [SILENT, architectural]

**What changed:** `ClientboundUpdateRecipesPacket` now only carries `RecipePropertySet`s and stonecutter
`SelectableRecipe`s. `getRecipes` is gone and so is `RecipeManager#replaceRecipes`. `ClientPacketListener#getRecipeManager`
became `recipes()`, which returns a `RecipeAccess` (`ClientRecipeContainer`) with no recipe list.
`Level#getRecipeManager` became `recipeAccess()`: `ServerLevel` returns a `RecipeManager` and `ClientLevel` only a
`RecipeAccess`. The recipe book receives only `RecipeDisplayEntry`s for unlocked recipes.

**Affected locations (everything built from client-side recipes)**
- `common/src/main/java/capsule/items/CapsuleItems.java:58-111`: `registerRecipesClient(RecipeManager manager)`. It iterates
  `manager.getRecipes()` (l.78) on the client, and its output feeds:
  - `common/src/main/java/capsule/itemGroups/CapsuleCreativeTabs.java:26-42` (creative tab contents),
  - `common/src/main/java/capsule/plugins/RecipeViewerContent.java:56-105` (JEI/REI/EMI content),
  - `common/src/main/java/capsule/plugins/jei/CapsulePlugin.java:39-43`, `plugins/rei/CapsuleReiPlugin.java:24-30`, `plugins/emi/CapsuleEmiPlugin.java:33-40`.
- [SILENT→crash] `fabric/src/main/java/capsule/fabric/mixin/ClientPacketListenerMixin.java:20-27`: `@Shadow private RecipeManager recipeManager`
  plus an `@Inject` into `handleUpdateRecipes` at `RecipeManager;replaceRecipes(Ljava/lang/Iterable;)V`. Neither the field
  nor the call exists any more, and with `"defaultRequire": 1` the mixin fails to apply and crashes the game.
  It is listed in `fabric/src/main/resources/capsule.mixins.json:9`.
- [COMPILE/loader] `neoforge/src/main/java/capsule/neoforge/CapsuleNeoForgeClient.java:51`: `RecipesUpdatedEvent` → `event.getRecipeManager()`.
  NeoForge reworked this event with the recipe-sync change; NeoForge 21.4+ has `OnDatapackSyncEvent#sendRecipes(RecipeType...)`
  and the client `RecipesReceivedEvent` (NeoForge API, not in the primer, so check the target NeoForge version).
- `common/src/main/java/capsule/recipes/PrefabsBlueprintAggregatorRecipe.java:281-308`: the `STREAM_CODEC` that shipped
  prefab sub-recipes to the client through the recipe sync. It no longer runs on dedicated servers, so client-side
  `PrefabsBlueprintAggregatorRecipe.instance.recipes` stays empty.
- `common/src/main/java/capsule/CapsuleMod.java:58-59` and the Javadoc at `PrefabsBlueprintAggregatorRecipe.java:55-61`
  ("before RecipesUpdatedEvent").

**Instructions (recommended, loader-agnostic)**
1. Make the list computation server-side: rename `CapsuleItems.registerRecipesClient(RecipeManager)` to
   `computeRecipeLists(RecipeManager manager, HolderLookup.Provider registries)`. Drop the `Minecraft`/`ClientLevel` lookup
   (l.69-74) and use `registries`. Call it from `CapsuleMod.serverStarting` after `populateRecipes`, and after every datapack
   reload (NeoForge `OnDatapackSyncEvent` with a null player, or Fabric `ServerLifecycleEvents.END_DATA_PACK_RELOAD`).
2. Add an S2C payload, for example `CapsuleRecipeListsToClient`, carrying the resulting stacks: capsuleList keys,
   opCapsuleList keys, unlabelled, deployed, recovery, blueprintChanged, upgraded, blueprintCapsules, blueprintPrefabs.
   Also include the data the viewers need (the upgrade `Ingredient` via `Ingredient.CONTENTS_STREAM_CODEC`, and the
   blueprint/prefab `ShapedRecipe`s via `RecipeSerializer.SHAPED_RECIPE.streamCodec()`, which still exists in 1.21.2).
   Encode stack lists with `ItemStack.STREAM_CODEC.apply(ByteBufCodecs.list())`. `ItemStack#LIST_STREAM_CODEC` was
   **removed** in 1.21.2 (primer "List of Removals").
3. Send it on join and after reload (NeoForge `OnDatapackSyncEvent`, Fabric `ServerLifecycleEvents.SYNC_DATA_PACK_CONTENTS`).
   Its client handler fills the `CapsuleItems` statics and forces a creative-tab rebuild. `CreativeModeTabs.tryRebuildTabContents`
   only rebuilds when its parameters change, so call `CapsuleCreativeTabs.CAPSULE_TAB.get().buildContents(new CreativeModeTab.ItemDisplayParameters(features, hasOp, registries))`.
4. Delete `ClientPacketListenerMixin.java` and remove `"ClientPacketListenerMixin"` from `capsule.mixins.json:9`. Remove the
   `RecipesUpdatedEvent` listener at `CapsuleNeoForgeClient.java:51`.
5. Recipe viewers (JEI/REI/EMI) for 1.21.2+ have their own recipe-transport strategies, and their APIs changed too. They are
   outside the primer, so check them against the chosen viewer versions. The client smoke tests in
   `common/src/gametest/java/capsule/clientsmoke/*Probe.java` will show whether the viewers still list the capsules.

Alternative: use the loader recipe-sync APIs instead (NeoForge `OnDatapackSyncEvent#sendRecipes` + `RecipesReceivedEvent`;
Fabric API's recipe sync, if the target Fabric API has one). This keeps more of the existing code, but it is two loader
implementations behind `capsule.platform`.

**Later versions:** the recipe-sync model stays server-only through 26.x. The loader opt-in APIs are where things change.

### 6.2 `Recipe` interface changes [COMPILE]

**What changed (primer l.1609-1650, l.1806-1847):**
- `Recipe#canCraftInDimensions(int,int)` **removed** (now hardcoded in `matches`).
- `Recipe#getResultItem(HolderLookup.Provider)` **removed** and replaced by `display()` (`List<RecipeDisplay>`).
  `getToastSymbol` became `getCategoryIconItem`.
- `Recipe#getIngredients()`/`isIncomplete()` **removed** and replaced by the abstract `placementInfo()` (`PlacementInfo`).
  Use `PlacementInfo#ingredients()` or `isImpossibleToPlace()`, and `PlacementInfo.NOT_PLACEABLE` for non-placeable recipes.
- `getGroup()` became `group()`. New `recipeBookCategory()` (`CraftingRecipe` provides a default from `category()`).
  `getRemainingItems` moved to `CraftingRecipe` with the same signature.
- `ShapedRecipePattern` now holds a `List<Optional<Ingredient>>`, and `ShapedRecipe#getIngredients()` returns
  `List<Optional<Ingredient>>`. `ShapelessRecipe` takes a `List<Ingredient>`.
- `RecipeHolder` now takes a **`ResourceKey<Recipe<?>>`** (`id()` returns a `ResourceKey`; use `.location()` for the
  `ResourceLocation`).
- `RecipeManager`: `getAllRecipesFor`, `byType` and `replaceRecipes` were removed. `byKey` takes a `ResourceKey`.
  `getRecipes()` still returns `Collection<RecipeHolder<?>>`.
- `CustomRecipe$Serializer` replaces `SimpleCraftingRecipeSerializer` (renamed).
- Not stated in the primer, but true of the 1.21.2 sources: `Recipe#getSerializer()` now returns
  `RecipeSerializer<? extends Recipe<T>>` (`CraftingRecipe`: `? extends CraftingRecipe`, `CustomRecipe`:
  `? extends CustomRecipe`). An override returning `RecipeSerializer<?>` no longer compiles; return the concrete type.

### 6.3 Ingredient JSON format [DATA]

**What changed (primer "The Ingredient Shift", "Holder Set Transition"; Misode changelog under "Pack Changes"):**
ingredients are a `HolderSet<Item>`. In JSON an ingredient is now a **string** (`"minecraft:paper"`), a **tag string**
(`"#c:ingots/iron"`) or a **list of item strings** (`["a:b", "c:d"]`). The `{"item": …}`/`{"tag": …}` object forms are no
longer accepted, and the recipe fails to load. Results (`{"id","count","components"}`) are unchanged.

**Affected files (every `"item"`/`"tag"` ingredient object, all under `common/src/main/resources/data/capsule/recipe/`).**
The count is the number of ingredient objects per file:
- `addons_capsule_{aluminum,brass,bronze,constantan,copper,electrum,enderium,invar,lead,lumium,nickel,osmium,platinum,signalum,silver,steel,tin,uranium,zinc}.json`: 19 files, 5 objects each, in `key` `#`, `b`, `e`, `i`.
- `capsule_{amethyst,diamond,emerald,gold,iron,netherite,obsidian,op,prismarine,quartz,wood}.json`: 11 files, 4 objects each.
- `captureblock.json` (4), `blueprint.json` (7: `"c"` is an array of 4 identical `{"item":"capsule:capsule"}` objects, plus `b`, `p`, `l`),
  `recovery.json` (2, in `ingredients`), `upgrade.json` (1, `ingredient`).
- Unaffected: `blueprint_change.json`, `clear.json`, `dye.json`, `aggregate_all_prefabs.json` (type only).
- The `neoforge:conditions`/`fabric:load_conditions` blocks in the addon files are loader features and stay as they are.

**Instructions (mechanical):** `{"item": "X"}` → `"X"`, `{"tag": "T"}` → `"#T"`. In `blueprint.json`, `"c": [ {...}x4 ]` → `"c": "capsule:capsule"`.
Example for `capsule_iron.json`:
```json
"key": { "#": "#c:ingots/iron", "b": "minecraft:stone_button", "e": "#c:ender_pearls", "i": "#c:ingots/iron" }
```
`recovery.json`: `"ingredients": ["capsule:capsule", "minecraft:glass_bottle"]`. `upgrade.json`: `"ingredient": "minecraft:popped_chorus_fruit"`.

**Generated and user-config JSON (also affected):**
- `common/src/main/resources/data/capsule/initialconfig/root/prefab_blueprint_recipe.json`: keys `b`, `p`, `l` → `"minecraft:stone_button"`, `"minecraft:paper"`, `"minecraft:blue_dye"`.
- `common/src/main/java/capsule/recipes/PrefabsBlueprintAggregatorRecipe.java:149-152` (`FixIngredient`) writes
  `{"item": id}` into the template: `template.getAsJsonObject("key").add(key, new JsonPrimitive(BuiltInRegistries.ITEM.getKey(...).toString()));`
- **Existing installs** have the old `prefab_blueprint_recipe.json` copied into `config/capsule/` (read at `helpers/Blueprint.java:230`).
  After `Files.readJSON`, add a small migration pass over `key`: a `JsonObject` with `item` becomes its string, and one with
  `tag` becomes `"#"+tag`. Rewriting the file is optional.
- Pre-existing bug, not a 1.21.2 change: `data/capsule/advancement/recipes/tools/capsule.json:22` (`{"tag": "c:ender_pearls"}`),
  `capsule_wood.json:14` (`{"tag": "minecraft:planks"}`) and `captureblock.json:14` (`{"item": "minecraft:compass"}`) use the
  pre-1.20.5 item-predicate form. The `ItemPredicate` codec ignores those fields, so the predicate matches any item. The
  correct form is `{"items": "#c:ender_pearls"}` / `{"items": "minecraft:compass"}`. Fix it while touching these files.

**Later versions:** the string/HolderSet ingredient format is stable.
